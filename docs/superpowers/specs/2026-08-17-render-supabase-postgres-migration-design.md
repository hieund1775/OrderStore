# Thiết kế Production Hardening và Migration PostgreSQL/Supabase

> Ngày: 17/08/2026  
> Trạng thái: Đã được chủ dự án duyệt trong hội thoại  
> Ưu tiên: Thực hiện trước khi tiếp tục Phase 3  
> Đích triển khai: Frontend và Express API trên Render, PostgreSQL managed bởi Supabase

## 1. Bối cảnh

Backend hiện dùng SQL Server qua `mssql`/`msnodesqlv8` và có nhiều T-SQL production query. Database live có 31 bảng, 1.022 orders, không phát hiện orphan ở các quan hệ order chính, foreign key/check constraint đều trusted và các index Phase 2 cần thiết đang tồn tại.

Tuy vậy, hệ thống chưa sẵn sàng production vì OTP cố định/lưu RAM, nhiều route trả raw `err.message`, rate limit chưa cấu hình reverse proxy, PayOS expiry chạy bằng `setInterval`, dependency audit có cảnh báo và schema nguồn đã drift so với database live.

Chủ dự án chọn:

- Supabase chỉ cung cấp PostgreSQL managed database, không dùng Supabase Auth/REST cho nghiệp vụ trong đợt này.
- Express trên Render tiếp tục sở hữu JWT, Google login, OTP, RBAC, PayOS và business logic.
- Giữ schema cho loyalty, recruitment và inventory nhưng không mở rộng tính năng trong migration.
- Chấp nhận maintenance window ngắn để cutover; không dual-write.

## 2. Mục tiêu

- Loại các blocker bảo mật/runtime trước khi public production.
- Chuyển schema, dữ liệu và production queries từ SQL Server sang PostgreSQL/Supabase.
- Giữ nguyên public URL, response contract và nghiệp vụ đã được Phase 1/2 bảo vệ.
- Có migrations tăng dần, staging rehearsal, đối soát dữ liệu và rollback rõ ràng.
- Chỉ tiếp tục Phase 3 sau khi PostgreSQL staging đạt nghiệm thu.

## 3. Ngoài phạm vi

- Không chuyển sang Supabase Auth trong đợt này.
- Không cho frontend truy cập trực tiếp các bảng nghiệp vụ qua Supabase anon API.
- Không dùng Supabase Realtime thay polling.
- Không hoàn thiện loyalty, recruitment-by-store hoặc inventory recipe.
- Không dual-write SQL Server và PostgreSQL.
- Không refactor toàn bộ route theo Phase 3 trong cùng migration.
- Không xóa SQL Server ngay sau cutover.

## 4. Kiến trúc đích

```text
Frontend on Render
  → Express API on Render
      → pg Pool / transaction client
          → Supabase PostgreSQL
      → PayOS
      → Google Identity verification
      → SMS/OTP provider

Render Cron Job
  → shared backend service
      → PostgreSQL advisory lock
      → expire/retry jobs
```

Backend dùng package `pg` và `DATABASE_URL`. Supabase client SDK không nằm trong data-access path. Service database credential chỉ tồn tại trên Render; frontend không nhận password, service-role key hoặc connection string.

Supabase pooler được dùng theo mode tương thích với web service Render. Pool trong Node phải nhỏ và cấu hình bằng environment để tổng connection không vượt giới hạn project. Kết nối production bắt buộc SSL với cơ chế xác minh phù hợp nhà cung cấp; không dùng cấu hình tương đương `encrypt: false`/tin mọi certificate.

## 5. Database adapter và transaction

### 5.1. Contract

Adapter PostgreSQL giữ interface ứng dụng tối thiểu:

```text
db.query(sql, params) → [rows, affected]
db.transaction(fn) → result
```

Placeholder được chuẩn hóa thành `$1`, `$2`, ...; không inline value. Trong transaction, mọi query của callback phải dùng cùng một `pg.Client`, sau đó commit/rollback và release trong `finally`.

### 5.2. Chuyển đổi T-SQL

- `TOP n` → `LIMIT n`.
- `GETDATE()` → `CURRENT_TIMESTAMP`/`NOW()`.
- `OUTPUT INSERTED...` → `RETURNING ...`.
- `UPDLOCK/ROWLOCK/HOLDLOCK` → `SELECT ... FOR UPDATE` trong transaction phù hợp.
- `ISNULL` → `COALESCE`.
- `DATEPART` → `EXTRACT`/`date_trunc`.
- `FOR JSON PATH` → `jsonb_agg/jsonb_build_object` hoặc mapping trong Node.
- `IDENTITY` → `GENERATED BY DEFAULT AS IDENTITY`.
- SQL Server catalogs/DMV/ShowPlan được thay bằng PostgreSQL catalogs và `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` chỉ trong benchmark/test tools.

Không dùng regex runtime để dịch T-SQL. Mỗi production query được chuyển và kiểm thử theo domain.

## 6. Schema PostgreSQL

### 6.1. Nhóm bảng giữ lại

- Identity/profile: `users`.
- Store: `stores`, `tables`.
- Catalog: `categories`, `products`, `size_options`, `base_options`, `sugar_options`, `ice_options`, `toppings`.
- Orders: `orders`, `order_items`, `order_item_toppings`, `order_status_history`.
- Promotions: `promotions`, `promotion_stores`, `voucher_usage_history`.
- Customer engagement: `reviews`, `wishlists`, `notifications`.
- Loyalty: `tier_rules`, `rewards`, `point_transactions`, `user_vouchers`.
- Recruitment: `jobs`, `job_stores`, `job_applications`.
- Inventory: `ingredients`, `ingredient_logs`.
- Operations: `audit_logs`.

Các module loyalty/recruitment/inventory được migrate để giữ đường phát triển và dữ liệu, nhưng không được claim là hoàn thiện nghiệp vụ.

### 6.2. Chỉnh cấu trúc

- Primary key dùng `bigint generated by default as identity` cho bảng nghiệp vụ.
- Timestamp dùng `timestamptz`; date-only giữ `date`.
- Tiền VND dùng `bigint`, không dùng floating point.
- Flags dùng `boolean`.
- Tags/amenities có cấu trúc dùng `jsonb` và được validate khi import.
- `users.phone` và `users.email` nullable; tạo unique partial index trên giá trị không null đã normalize.
- Thêm `users.token_version integer not null default 0` để revoke JWT của user.
- Google identity dùng bảng `user_identities` với `(provider, provider_subject)` unique, không dùng email làm định danh provider lâu dài.
- `promotion_stores` là nguồn quan hệ áp dụng theo store. `promotions.scope` chỉ được giữ tạm như display/legacy text và không dùng để authorize/tính eligibility.
- Snapshot `product_name`, unit price và topping name/price trong order details được giữ nguyên.

### 6.3. Bảng bổ sung

#### `user_identities`

Liên kết user nội bộ với Google hoặc provider tương lai. Không lưu OAuth access token nếu ứng dụng không cần gọi API provider.

#### `otp_codes`

Lưu `phone_normalized`, `code_hash`, `attempt_count`, `expires_at`, `consumed_at`, `created_at`. Không lưu OTP plaintext. Query verify phải lock record phù hợp, tăng attempts và consume atomically.

#### `payment_events`

Lưu provider, provider event/reference key, order reference, loại event, payload đã lọc, processing status/error code và timestamps. Provider event key unique để webhook retry idempotent.

#### `idempotency_keys`

Scope theo operation/user hoặc anonymous fingerprint; lưu request hash, response reference, status và expiry. Create-order retry với cùng key+payload trả kết quả cũ; cùng key khác payload bị reject.

#### `schema_migrations`

Là lịch sử migration duy nhất của PostgreSQL. Migrations chỉ tiến tới, có transaction khi PostgreSQL cho phép và không chứa drop/create toàn database.

#### `background_jobs`

Lưu job type, payload tối thiểu, status, attempts, available/locked timestamps và last error code. Dùng cho expiry/retry có độ tin cậy; không dùng làm queue tổng quát ngoài nhu cầu hiện tại.

### 6.4. Constraint tối thiểu

- `qty > 0`.
- Giá, subtotal, total, discount, points và stock không âm theo nghiệp vụ hiện tại.
- `discount_amount <= subtotal`, `total = subtotal - discount_amount` khi không có thành phần khác.
- `start_date <= end_date`.
- Role/admin/branch consistency: admin phải có role hợp lệ; non-super admin phải có branch; customer không có admin role.
- Order type, payment/status, history status và enum nghiệp vụ dùng check constraints tương ứng.
- Unique/index cho order code, PayOS references, customer history, order status latest, KDS filters, voucher use và FK thường join.

## 7. Production hardening trước migration

### 7.1. OTP và auth

- OTP dùng secure random, TTL ngắn, hash trước khi lưu và giới hạn attempts/resend.
- Tích hợp SMS provider thật; production không có demo/fixed OTP hoặc bypass.
- Rate limit theo normalized phone và IP.
- JWT verification kiểm tra `token_version` khi cần revoke; secret production đủ mạnh và chỉ nằm trong Render secrets.

### 7.2. Error handling và logs

- Central async/error middleware phân biệt validation, business, provider và infrastructure errors.
- Production response không trả raw SQL/provider message, stack hoặc query.
- Log structured có request ID/error code; redact Authorization, OTP, PayOS secret và PII nhạy cảm.

### 7.3. Render runtime

- Đặt `app.set('trust proxy', 1)` theo topology Render đã xác minh.
- Rate-limit store dùng shared store nếu scale nhiều instance; một instance chỉ là phương án staging tạm thời.
- Tách `app` khỏi `listen` để test không bind port.
- Pin Node 22 trong `package.json`/Render config và dùng clean install từ lockfile.
- Xử lý toàn bộ high/critical production dependency advisories trước release.
- Swagger production bị tắt hoặc bảo vệ.
- Có graceful shutdown: ngừng nhận request, chờ in-flight, đóng pool.

### 7.4. Health

- `/live`: chỉ chứng minh process/event loop hoạt động.
- `/ready`: query PostgreSQL nhẹ có timeout và chỉ trả trạng thái chung.
- Health response không lộ version DB, host, credential hoặc stack.

## 8. Scheduler và webhook

`setInterval` bị loại khỏi web process. Render Cron gọi command riêng dùng cùng payment service. Command lấy PostgreSQL advisory lock để tránh hai worker xử lý cùng đợt.

PayOS webhook thực hiện theo flow:

1. Verify signature.
2. Insert/upsert `payment_events` theo provider event key.
3. Trong transaction, lock order hoặc chạy CAS có điều kiện amount/provider/status.
4. Ghi result vào payment event.
5. Retry cùng event trả kết quả idempotent.

Không ghi full secret/signature hoặc payload nhạy cảm không cần thiết.

## 9. Chiến lược chuyển query theo domain

Thứ tự:

1. Environment, adapter, migrations và health.
2. Auth/users/OTP/Google identity.
3. Catalog/stores/public reads.
4. Promotions/voucher.
5. Orders create/lookup/history/cancel.
6. Admin order/KDS/payment/webhook.
7. Dashboard/reports/settings/engagement.
8. Perf tools và SQL integration tests.

Mỗi domain phải có production-path contract tests trước khi bỏ query SQL Server tương ứng. Không giữ hai dialect trong cùng production handler sau khi domain đã cut over.

## 10. Data migration

### 10.1. Staging rehearsal

- Snapshot SQL Server read-only source.
- Export theo bảng với encoding Unicode và timestamps rõ timezone assumption.
- Transform type, normalize phone/email, validate JSON và preserve IDs.
- Import theo thứ tự foreign key.
- Reset PostgreSQL identity sequences lớn hơn max imported ID.
- Chạy đối soát và integration smoke tests.
- Diễn tập toàn bộ ít nhất một lần trên Supabase staging trước production.

### 10.2. Đối soát

Bắt buộc so sánh:

- Row count mọi bảng và checksum/aggregate cho bảng lõi.
- Không orphan FK.
- Unique/check constraints không vi phạm.
- Tổng `orders.subtotal/discount/total` theo ngày và toàn bộ dataset.
- Count/tổng `order_items` theo order.
- Latest status mỗi order.
- PayOS references/payment status.
- User phone/email identity mapping.
- JSON parse success cho tags/amenities.

Sai lệch bảng lõi hoặc tổng tiền bằng bất kỳ giá trị nào đều chặn cutover, trừ sai lệch đã được chủ dự án duyệt bằng văn bản.

## 11. Cutover và rollback

### 11.1. Cutover

1. Xác nhận backup SQL Server và Supabase restore capability.
2. Bật maintenance mode chặn mọi write endpoint; read có thể giữ nếu không gây nhầm trạng thái.
3. Chờ in-flight transaction kết thúc.
4. Export/import delta cuối theo khóa/timestamp đã định nghĩa và chạy đối soát.
5. Reset sequences và chạy migrations cuối.
6. Cập nhật Render `DATABASE_URL`/pool configuration.
7. Deploy backend PostgreSQL, chạy `/live`, `/ready` và smoke suite.
8. Mở write traffic khi toàn bộ gate đạt.

### 11.2. Rollback

Nếu readiness, smoke hoặc data check thất bại trước khi mở write traffic, đổi Render về SQL Server config/build trước và tắt PostgreSQL writer.

Sau khi đã mở write traffic trên PostgreSQL, không tự động quay lại SQL Server vì sẽ mất các write mới. Khi đó giữ maintenance mode, export PostgreSQL delta và thực hiện rollback theo runbook có đối soát. SQL Server được giữ read-only trong thời gian ổn định đã thống nhất; không xóa ngay.

## 12. Test strategy

- Unit tests cho adapter parameterization, error mapping, OTP/hash/idempotency và data transforms.
- Contract HTTP tests hiện có tiếp tục chạy không đổi expected behavior.
- PostgreSQL integration tests chạy trên database disposable/dedicated, không mock.
- Concurrency tests thật cho create-order idempotency, voucher consume, cancel/status transition và PayOS CAS/webhook retry.
- Migration tests chạy fresh database từ migration zero và upgrade path từ snapshot staging.
- Reconciliation tests sinh báo cáo machine-readable.
- Render staging smoke kiểm tra auth, catalog, create/lookup/cancel order, KDS, payment status và cron command.

## 13. Acceptance

Đợt migration chỉ PASS khi:

- Không còn `mssql`, `msnodesqlv8` hoặc T-SQL trong production paths.
- Fresh PostgreSQL database dựng được hoàn toàn từ migrations và seed được phân loại rõ demo/production.
- Backend full suite và PostgreSQL integration suite xanh.
- OTP cố định/bypass production đã bị loại bỏ.
- Raw SQL/provider error không xuất hiện trong production responses.
- Render staging kết nối Supabase pooler ổn định; `/live` và `/ready` đạt.
- Reconciliation đạt 100% cho bảng lõi/tổng tiền và không có orphan.
- PayOS webhook/expiry idempotent và scheduler không nằm trong web process.
- Dependency audit không còn high/critical production finding chưa được chấp nhận rõ.
- Cutover và rollback runbook đã được diễn tập trên staging.

Sau khi các điều kiện trên PASS, Phase 3 tiếp tục với domain repositories PostgreSQL. Không quay lại refactor repository SQL Server.
